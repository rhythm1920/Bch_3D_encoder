How the 3-D BCH encoder code works

This walkthrough first derives the maths that every file relies on. It then goes through each function and says what the code actually computes, line by line where that matters. It explains why the computation is correct and gives real values from the N=15, T=2 build. Field: GF(16) built from x⁴+x+1, with N = 15, K = 3,163 message bits and 3,375 codeword bits.

The maths, once

1 · GF(16) as 4-bit integers

An element of GF(16) is a polynomial of degree at most 3 over GF(2), stored as a 4-bit integer (bit r is the coefficient of xr). Addition is XOR. α = x = 0b0010 generates the multiplicative group, and multiplying by α is a left shift. When bit 4 appears, it is replaced using x⁴ = x + 1, which means XOR with 0b10011.

Powers of α, as computed by the code: α⁰…α¹⁴ = 1, 2, 4, 8, 3, 6, 12, 11, 5, 10, 7, 14, 15, 13, 9. For example α⁴ = 16 ⊕ 19 = 3 = x + 1, and α¹⁵ = 1 again.

Two facts are used everywhere. First, squaring is linear in characteristic 2, since (a+b)² = a² + b². Second, the subfield GF(2d) ⊂ GF(16) is exactly the set of elements with a2d = a. Its nonzero elements are the powers of γ = α15/(2d−1): for d = 2, γ = α⁵ = 6, and for d = 1, γ = 1.

2 · The codeword is a 3-D inverse DFT

A codeword is a 15×15×15 binary cube c(i), with i = (i, i', i''). Its spectrum is a 15×15×15 cube C(J) over GF(16):

C(J) = Σᵢ c(i) · α^(i·J) c(i) = Σ_J C(J) · α^(−i·J)

Here i·J = i·j₁ + i'·j₂ + i''·j₃ (mod 15). The usual 1/N factor of the inverse transform is 1/15, and in characteristic 2 that is 1 because 15 is odd, so no scaling appears anywhere in the code. The kernel factorises as α^(−i·J) = α^(−i j₁)·α^(−i' j₂)·α^(−i'' j₃), so the 3-D transform can be computed as three passes of 1-D transforms, one per axis. That is the "separable IDFFFT".

The encoder works in the spectral domain. It writes the message into the spectrum C, forces the null positions to 0, and inverse-transforms. Every output bit is a GF(2)-linear function of the message.

3 · Conjugate classes: why the output is binary

If c is binary then c(i)² = c(i), and squaring is linear, so

C(J)² = Σᵢ c(i)² α^(2 i·J) = C(2J)

The spectrum is therefore not free: C(2J) is fixed by C(J). The orbit J → 2J → 4J → … (mod 15 per coordinate) is a conjugate class. Since 2⁴ = 16 ≡ 1 (mod 15), every orbit has size d ∈ {1, 2, 4}. Going once around the orbit gives C(J)2d = C(J), so the class value lies in the subfield GF(2d) and carries exactly d bits.

(0,1,2) → (0,2,4) → (0,4,8) → (0,8,1) → back, size 4, 4 message bits.
(0,0,5) → (0,0,10), size 2, value in GF(4) = {0, 1, α⁵, α¹⁰}, 2 bits.
(0,0,0), size 1, value in GF(2), 1 bit.

Conversely, any spectrum that obeys C(2J) = C(J)² inverse-transforms to a binary cube. The encoder therefore picks one value S per class, puts S, S², S⁴, S⁸ along the orbit, and the result is guaranteed to be binary.

4 · The trace formula the hardware implements

Group the inverse-DFT sum by classes. For class k with representative Jk, the orbit members are 2uJk, with values Sk2u:

c(i) = Σ_k Σ_{u<d} S_k^(2^u) · α^(−2^u i·J_k) = Σ_k Σ_{u<d} (S_k · α^(e_k(i)))^(2^u) = Σ_k Tr_d( S_k · α^(e_k(i)) )

e_k(i) = −(i·J_k) mod 15

Trd(x) = x + x² + … + x2d−1 is the trace from GF(2d) down to GF(2), so each term is a single bit. One codeword bit is the XOR over the 798 classes of one trace bit per class.

Each trace is a GF(2)-linear function of the 4 bits of Sk, so it equals the parity of Sk AND some 4-bit mask, and that mask depends only on (k, e). This is the key to all three hardware designs. A "multiplier" S·αe followed by a trace collapses to an XOR of 1–4 wires. The whole encoder is XOR gates.

The exponent ek(i) takes only 15/gcd(15, j₁, j₂, j₃) distinct values. That gives 15 values for most classes, 5 when all coordinates are multiples of 3, 3 when they are multiples of 5, and 1 for J = 0. These sets are the computation classes: 754 classes × 15 + 30 × 5 + 13 × 3 + 1 × 1 = 11,500 distinct products.

5 · The null cube and where K = 3,163 comes from

The code is defined by C(J) = 0 for every J in the cube 1 ≤ j₁, j₂, j₃ ≤ 2T = 4. In each dimension this makes α¹…α⁴ roots, the BCH design for T = 2. A class that touches the cube must be 0 as a whole, because one zero member forces the rest by squaring. Those classes carry no message.

N=15, T=2: there are 851 classes. The 53 null classes cover 212 spectral positions, for example (1,1,1)→(2,2,2)→(4,4,4)→(8,8,8). The 798 remaining classes carry 784×4 + 13×2 + 1×1 = 3,163 bits = K, and 3,375 − 212 = 3,163.

6 · Linearity, which the verification relies on

The map message → codeword is GF(2)-linear. The message is packed into the Sk by XORs, each trace is linear, and the outputs are XORs. So codeword(a ⊕ b) = codeword(a) ⊕ codeword(b), and the encoder is fully described by its K × 3,375 generator matrix, whose row b is the codeword of the unit message 1≪b. The RTL is also pure XOR, with no constants and no inverters, so it is linear too. Two linear maps that agree on all K unit vectors agree on all 23163 messages. This is why the testbench checks all 3,163 unit vectors.

model/bch3d.py: the golden model

BCH3DModel.__init__(N=15, T=2, prim_poly=0b10011)

It computes M = bit_length(N+1) − 1 = 4 and asserts that N = 2M − 1. It then builds two tables in one loop: x starts at 1, and each step stores exp[e] = x and log[x] = e, shifts x left, and XORs with prim_poly if bit M is set. This is exactly the "multiply by α" step from §1.

exp has length 2N + 2, and the second half repeats the first (exp[e+N] = x). That lets mul index exp[log a + log b] without a mod, since the sum is at most 28. It finishes with _build_classes(), K = sum of class sizes = 3,163, and N_CLASS = 798.

mul(a, b) and sq(a)

mul returns 0 if either input is 0, and otherwise exp[log[a]+log[b]], using αx·αy = αx+y. sq is the same with b = a, i.e. exp[2·log a].

mul(6, 12): log 6 = 5 and log 12 = 6, so the result is exp[11] = 14. Checking by polynomials: (x²+x)(x³+x²) = x⁵+x³ = x³+x²+x = 14.

trace_d(a, d)

It accumulates a ⊕ a² ⊕ a⁴ ⊕ … over d terms, squaring with sq at each step, and then asserts that the result is 0 or 1. That assertion only holds for a ∈ GF(2d): the partial trace of an element outside the subfield is not binary. This function is used for checking. The production masks are derived differently (see _build_classes).

lin_to_pt, pt_to_lin, _in_null_cube

The cube is flattened as p = i·225 + i'·15 + i''. lin_to_pt inverts this with (p//225, (p//15)%15, p%15). Everything uses this layout: codeword bit p of the RTL, of the Python integers and of the testbench vectors. _in_null_cube is true if all three coordinates are in [1, 2T].

_build_classes(): the heart of the model

For every linear index p from 0 to 3,374, in increasing order:

  1. Orbit. It walks nxt(pt) = (2a, 2b, 2c) mod N until it returns to pt. This is the Frobenius orbit from §3.
  2. Representative. If p is not the smallest linear index in its orbit, it skips the point, since that class will be (or was) built from its smallest member. Classes are therefore created in ascending order of representative. That order is the message-bit order, and the Verilog uses the same rule.
  3. Null check. If any orbit member is in the null cube, the orbit goes to null_classes and gets no message bits.
  4. sub_masks. The class takes d message bits b₀…b_{d−1} starting at off and packs them into a subfield element S = Σ bᵢ·γi, with γ = αstep and step = N/(2d−1). Bit r of S is then the parity of the bᵢ for which bit r of γi is 1, and sub_masks[r] records which i those are.
  5. distinct_exps. It loops over all 3,375 points, collects e = −(i·J) mod N into a set and sorts it. The set has the 15/5/3/1 values from §4.
  6. trace_masks[e]. For each basis bit r, it computes Trd(αr·αe) with the same square-and-add loop and keeps bit 0. The mask bit r is that bit, so Trd(S·αe) = parity(S & mask).

Why "keep bit 0" is correct. For d = 4 every trace is already 0 or 1. For d < 4, αr is generally not in GF(2d), so Trd(αr·αe) can be any field element. However, x ↦ bit0(Trd(x)) is GF(2)-linear on all of GF(16). For x = S·αe with S ∈ GF(2d), it gives Trd(x) exactly, because αe is also in GF(2d): J has orbit size d, so (2d−1)J ≡ 0 and e is a multiple of 15/(2d−1), and the trace is binary there. A linear map that is right on the subspace that S actually occupies is all the hardware needs.

Class 7, rep (0,1,2), size 4, message bits 23–26: sub_masks = [1,2,4,8], so S is the 4 message bits as they are. Trace masks: e=0 → 8, so Tr(S) = S₃, since for x⁴+x+1 the traces of 1, α, α² are 0 and Tr(α³) = 1. e=14 → 1, so Tr(S·α¹⁴) = S₀. e=11 → 15, so the trace is the XOR of all four bits.

Class 3, rep (0,0,5), size 2: γ = α⁵ = 0110, so S = b₀·0001 ⊕ b₁·0110, giving sub_masks = [1,2,2,0] (bits 1 and 2 of S both copy b₁). distinct_exps = [0, 5, 10] and the trace masks take values {4, 11, 15}.

Class 0, rep (0,0,0), size 1: S = b₀, and its single trace mask is 1. This is the "DC" bit, which contributes b₀ to every codeword bit.

msg_to_submsg(msg)

For each class it extracts bits = (msg ≫ bit_offset) & (2d−1), and bit r of Sk is the parity of bits & sub_masks[r]. It returns 798 four-bit values. This is §4's packing, and it is bit-exact with the Verilog module of the same name.

encode_idffft(msg): reference path 1, no trace masks

  1. It builds a 15×15×15 GF(16) array spec, all zeros (so null classes stay 0).
  2. For each class it walks the orbit, writing v and then setting v = sq(v), so the orbit gets S, S², S⁴, S⁸. This enforces C(2J) = C(J)².
  3. Three passes of idft1d: along i'' for every (a, b), then along i', then along i. idft1d is the direct O(N²) sum out[i] = Σⱼ vec[j]·α(−ij) mod N, skipping zeros.
  4. It asserts that every output is 0 or 1 (the binary property from §3) and packs bit p.

This path never touches trace_masks or distinct_exps. That independence is what makes it a meaningful check of everything derived from them.

encode_trace(msg): reference path 2, the hardware formula

For each point p and each class, it computes e = −(i·J) mod N and XORs the parity of S & trace_masks[e] into the bit. This is §4's formula exactly, the same computation the RTL performs. Its cost is 3,375 × 798 parities.

decode_dffft_check_nulls(cw)

It loads the binary cube and runs three forward 1-D DFTs, with α+ij, along the three axes. It then checks that every position in the null cube is 0. This tests the code definition itself, not just whether two encoders agree.

self_test()

For four (N, T) configurations and six messages (all zeros, all ones, the lowest bit, the highest bit and two random ones), it asserts encode_idffft == encode_trace and that the null check passes. For (15, 2) it also pins K = 3,163, 798 classes, 53 null classes and the computation-class histogram {15: 754, 5: 30, 3: 13, 1: 1}.

rtl/bch3d_msg_to_submsg.v

Constant functions, then a generate loop

This module recomputes the class structure inside Verilog at elaboration time, so the same file works for any (N, T, PRIM_POLY). The functions mirror the Python one for one:

  • log2_np1 gives M; alpha_pow(e) repeats the shift-and-reduce step e times.
  • next_pt doubles each coordinate of a linear index mod N. orbit_size, is_rep (no orbit member is smaller) and orbit_is_null walk the orbit.
  • count_classes and count_bits set the localparams N_CLASS = 798 and K_BITS = 3,163, which size the ports.
  • build_table packs, for class k, the bit offset into bits [32k, 32k+16) and the size into [32k+16, 32k+32) of one large constant TABLE. It is sized 32·N³ because Verilog-2001 can't size a constant by a value computed in the same pass, so it uses the upper bound.
  • sub_mask(r, d) is the same rule as Python's sub_masks: bit i is set if bit r of αi·N/(2d−1) is 1.

The generate block then emits, for each class k and each bit r: bits = msg[OFF +: SZ] (zero-extended to 32) and sub_msg[4k+r] = ^(bits & MASK). For size-4 classes each mask has one bit, so this is plain wiring. For size-2 classes, bits 1 and 2 are the same wire. Only the elaboration is expensive; the hardware has no LUTs.

model/gen_rtl.py: the hardware generators

Each generator writes Verilog as text. The Python does all the maths (exponents, masks, wiring), and the emitted RTL contains only wires and XORs.

_xor_expr, _s_mask_expr, _s_mask_off

_s_mask_off("S", off, mask, M) turns a 4-bit mask into the Verilog text S[off+r] ^ … for the set bits, or 1'b0 if the mask is empty. This is how "parity(S & mask)" becomes hardware. _s_mask_expr does the same without an offset. _xor_expr joins terms 16 per line for readability.

generate_baseline_rtl: design 1

For every point p, it builds the list bits_p: for every class k, the sub_msg bits picked by trace_masks[e_k(p)]. The output bit is the XOR of that whole list, a direct expansion of c(p) = ⊕k parity(Sk & mask). Each point is its own module instance (bch3d_base_pt_*_w<width>, one module per distinct width). With flatten none that hierarchy stops the tool from sharing the per-class parities between points: every point recomputes them.

Point (0,0,0): every e is 0, so each mask has one bit and the width is 798. Point (1,2,3): the width is 1,716, because a typical mask has about 2 bits. Over 3,375 points that is about 5.8 M XOR inputs, which explains the roughly 1.16 M LUTs without flattening.

generate_opt_rtl: design 2

  1. wire_map: one index for every (class, e) in distinct_exps, 11,500 in total.
  2. Multiplier units: one module per unique (size, exponent list) signature. Output p[j] = _s_mask_expr(s, trace_masks[e_j]), i.e. Tr(S·αe) as a 1–4 input XOR. Strictly, the "multiplier" in the name is multiply-then-trace, reduced to a parity.
  3. Bank: instantiates one unit per class on sub_msg[4k +: 4], writing into mul_out[lo +: n].
  4. Trees: for every point, a 798-input XOR of mul_out[wire_map[(k, e_k(p))]], exactly one wire per class.

Moving from design 1 to design 2 changes where the parity is formed. Design 2 computes each of the 11,500 products once and lets 3,375 trees share them, so each point sees 798 inputs instead of about 1,716. The cost is fan-out: one bank wire is read by up to 3,375/15 = 225 trees spread over the whole chip. That wiring is what failed to route.

slice_points, generate_baseline_slice_reg_rtl, generate_opt_slice_reg_rtl

slice_points(m, 0) returns the 225 linear indices with i'' = 0, which are p = 0, 15, 30, …, 3,360.

The baseline slice repeats design 1's per-point construction for those 225 points only. The opt slice builds a used dictionary keyed by (class, mask) rather than (class, e). Identical masks then share one wire, and only the products those 225 trees read are emitted, 10,608 of them. Each slice registers msg on input and the 225 outputs, so timing runs from register to register.

generate_core_slice_reg_rtl is the earlier approach: it wraps the full core and selects the 225 bits. It is correct in simulation, but synthesis has to build the whole core before removing the unused part, and that ran out of memory.

generate_reg_wrapper_rtl

It writes <core>_reg: msg_q <= msg, the combinational core on msg_q, then codeword <= cw_c. The latency is 2 cycles and it adds 6,538 FFs. Its only purpose is to give the timing tools a register-to-register path through the whole encoder.

generate_tm_rtl: design 3 core

The derivation. Split the exponent at point (i, i', c):

e_k(i,i',c) = −(i j₁ + i' j₂) − c·j₃ = e0_k(i,i') − c·j₃

Tr(S_k · α^(e0 − c j₃)) = Tr( (S_k · α^(−c j₃)) · α^(e0) )

So if a register holds Sk(c) = Sk·α−c·j₃, the fixed wiring for (i, i') with exponent e0 produces plane c. Each cycle the register is updated by S ← S·g with g = α−j₃, a constant per class. The product stays in GF(2d), because g is a power of α15/(2d−1) for the same reason as in §4.

What the code emits:

  • Bank: wires only for the exponents e0 that occur at i'' = 0. That gives 10,608 rather than 11,500: a class with j₁ = j₂ = 0, such as (0,0,1), needs only e0 = 0.
  • S_rot: a constant multiplication is a 4×4 GF(2) matrix whose column r is αr·g. The code computes cols[r] = mul(1<<r, g), and output bit q is the XOR of the S bits r whose column has bit q set.
  • 225 trees: u_tree_i_i' XORs mul_out[wire_map[(k, e0_k(i,i'))]] over the 798 classes.
  • Control: busy and a 4-bit counter cyc from 0 to 14. accept = start && (!busy || last), so a new message can be taken in the last cycle and codewords run back to back. On accept, S <= sub_msg; while busy, S <= S_rot. Every cycle, slice <= slice_c, with slice_valid and slice_idx delayed by one cycle to match. done marks slice 14.

Class 7, rep (0,1,2): j₃ = 2, so g = α−2 = α¹³ = 13 (1101). cols = [13, 9, 1, 2]. Reading bit q across the columns gives S_rot[0] = S₀⊕S₁⊕S₂, S_rot[1] = S₃, S_rot[2] = S₀, S_rot[3] = S₀⊕S₁. Classes with j₃ = 0 have g = 1, so S_rot = S and the rotation is just wiring.

generate_tm_asm_rtl: the assembly wrapper

For each group g = i·15 + i' (225 groups), it keeps a 15-bit shift register in cw_sr[g*15 +: 15]. On every slice_valid, the group shifts down and slice[g] enters at the top (bit 14). After 15 slices, the slice from cycle c sits at bit c, so cw_sr[g*15 + c] = bit (i, i', c). Its index is i·225 + i'·15 + c, which is exactly the flat codeword layout, so no reordering is needed. One cycle after done (done_d), the 3,375 bits are copied to a hold register codeword and cw_valid pulses. This adds only flip-flops, no LUTs.

generate_testbench: golden vectors via linearity

  1. For each class it builds exp_to_pts_mask[e]: a 3,375-bit integer of the points whose exponent is e.
  2. For each of the class's d bits it forms the unit sub-message s_val, which is column i of sub_masks, i.e. γi. The unit codeword is the XOR of the point masks of every e with parity(s_val & trace_masks[e]) = 1. This gives all K generator rows in O(K·15) big-integer XORs instead of O(K·3,375·798).
  3. fast_encode(msg) XORs the rows of the set bits (§6).
  4. Independent check: on 15 messages it asserts fast_encode == encode_idffft, which does not use the masks, and runs the null-cube check.
  5. It writes msg_*.mem and cw_*.mem with all zeros, all ones, all 3,163 unit vectors and the random messages: 3,170 vectors. The Verilog testbench drives each through both bch3d_enc_baseline and bch3d_enc_opt and compares them with the golden codeword and with each other.

The other testbench generators

  • generate_reg_wrapper_testbench and generate_baseline_slice_testbench are pipelined: one message goes in on each negedge, and the output is compared 2 cycles later with the golden codeword, or with its 225 slice bits selected as {cw[p_224], …, cw[p_0]}. The second one takes mod_name, so the design 2 slice reuses it.
  • generate_tm_testbench rebuilds the codeword from the slices with asm[a*225 + b*15 + slice_idx] = slice[a*15+b], compares it on done, and also tests a reset in the middle of a codeword.
  • generate_tm_asm_testbench checks codeword on each cw_valid.

main()

It parses --n --t --rtl-dir --tb-dir --vec-dir --num-random, builds the model, and writes everything in this order: baseline, opt, vectors and the main testbench, the TM core, the TM assembly wrapper, the register wrappers for both full designs, and the two slices with their testbenches. The full N = 15 RTL is about 83 MB for the baseline and 40 MB for opt.

model/bch3d_tm.py and model/bch3d_cse.py

encode_tm(m, msg): the TM schedule in software

It takes S = msg_to_submsg and step[k] = α−j₃. For each cycle 0–14, every (i, i') tree XORs parity(Sk & trace_masks[e0]) over the classes, and the result is placed at bit (i, i', cycle). Then S = [mul(s, g)]. self_test compares the result with encode_idffft: all unit vectors for N = 7, and 5 messages for N = 15. This is the proof that the rotation trick used by generate_tm_rtl is exact, independent of the RTL.

bch3d_cse.py: an XOR-sharing idea that was not built

Take a vector n of order 15 in Z₁₅³. Every class with J·n ≡ 0 (mod 15) has ek(p + m·n) = ek(p) − m(J·n) = ek(p). So the partial XOR over such a group G is constant along lines in direction n. It takes only 3,375/15 = 225 distinct values, and each can be computed once and shared by 15 output points.

  • normals_n15 combines one representative of each projective point of F₃³ (13) and of F₅³ (31) with the CRT, giving 403 directions of order 15.
  • build_groups greedily picks the normal that covers the most uncovered classes until all 798 are covered.
  • key_of(p, n) is the canonical point of p's line: the smallest of the 15 translates.
  • encode_cse computes one partial value per (group, line) and XORs one value per group at each point. It is checked against the IDFFFT.
  • cost counts level-1 XORs (225·(|G|−1) per group) and level-2 XORs (3,375·(groups−1)), with LUT6 estimates using 5 new inputs per LUT.

scripts/

gen_tb.py

A self-contained re-derivation of msg_to_submsg, with its own α powers, orbit walk and null test. Its enc packs bits as S ^= αi·step. It writes one testbench that instantiates the Verilog module for 4 configurations, (15,2), (15,1), (7,1) and (7,2), with 5 messages each. This is a check of the Verilog constant functions that doesn't depend on bch3d.py.

sim.ps1

It runs xvlog → xelab → xsim -R in a work directory, with -Glbl for netlist simulation. It exits 0 only if the log contains PASS and no FAIL or ERROR.

vivado_ooc.tcl and vivado_pnr.tcl

vivado_ooc.tcl runs out-of-context synthesis with the chosen -flatten_hierarchy mode and reports utilisation. vivado_pnr.tcl runs synthesis, then create_clock on clk, then input and output delays of 20% of the period on every port. It then runs opt_design → place_design → route_design (no phys_opt). It writes the timing summary, the 3 worst paths, flat and hierarchical utilisation, high-fanout nets, route status, vectorless power, congestion analysis, clock utilisation and a routed checkpoint, plus an optional funcsim netlist when WRITE_TIMESIM=1. The last line it prints is PNR_SUMMARY: … WNS=… WHS=…, which the background monitor greps for.
